# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Working with the user

Before writing any code or making any architectural/design decision, stop and interview the user first: ask questions, lay out the realistic options with their tradeoffs, and let them choose. Do not default to picking an approach and proceeding — decisions here are made collaboratively, one topic at a time.

Before making any automated database schema change (new/modified entities, EF Core configuration, migrations), show the user the proposed new schema and what it modifies — new tables/columns, changed constraints/indexes, affected existing tables — and get their go-ahead before generating the migration and applying it.

## Code style

Prefer C# string interpolation (`$"{a}-{b}"`) over `+`-based string concatenation wherever practical, for readability.

Prefer switch expressions (`x switch { ... }`) over traditional `switch`/`case` statements wherever practical.

**Treat compiler warnings as errors.** A change is not done while it introduces (or leaves) a build warning — fix the underlying cause rather than suppressing it, and don't merge with warnings outstanding. New code should build clean. **This is now enforced** (`docs/adr/0402-enforce-treat-warnings-as-errors.md`): `Directory.Build.props` sets `<TreatWarningsAsErrors>true</TreatWarningsAsErrors>` repo-wide (every project incl. tests), so any warning fails the build. NuGet package-audit warnings (`NU1901`–`NU1904`, deprecated/vulnerable) are excluded via `<WarningsNotAsErrors>` — the dedicated CI vulnerable-dependency scan (ADR 0379) owns vulnerability-blocking, so a freshly-published advisory can't break every local/CI compile mid-task. (Watch for the XML-comment `--` trap in that props file: a literal double-hyphen — e.g. writing out a `--flag` — makes the file fail to load with a misleading "Invalid framework identifier ''" restore error.)

**Use specific exception types, not bare `ApiException` with a string code.** A throw like `new ApiException("STORAGE_QUOTA_EXCEEDED", StatusCodes.Status409Conflict, "…")` is **not acceptable** — instead throw a dedicated, intent-named subclass that encapsulates the code/status/message. Exceptions form a **two-level hierarchy**: a per-area **base** class inherits from `ApiException` (e.g. `StorageException : ApiException`), and each concrete error inherits from that area base (e.g. `StorageQuotaExceededException : StorageException`), so a caller can `catch` a whole area or a single error. The classes live under `src/SimplArchive.Api/Errors/Exceptions/<Area>/` (one file per class), named with the `Exception` suffix. This keeps the error code/status defined once at the type and makes throw sites read intent-first (`throw new StorageQuotaExceededException(…)`). The global handler translates any `ApiException` (base or subclass) into the RFC 7807 response. When you add a new error condition, add (or reuse) a specific subclass under the right area base rather than a new string literal. **The whole codebase is now bare-`ApiException`-free** — every throw is a dedicated subclass across ~19 areas (Storage/Workflow/Acl/Authorization/Search/LegalHolds/Checkout/Passkeys/Import/Tenant/Principals/Concurrency/Annotations/Archive/References/Comments/Documents/Ocr/Inbox/Audit/Diagnostics), and a **unit test guards it**: `SimplArchive.UnitTests/NoBareApiExceptionTests` scans `src/` and fails the build if a bare `new ApiException(...)` reappears. Cross-cutting codes shared by several controllers get one exception with static factories (e.g. `InsufficientRightsToGrantException.OnDocument()/OnServiceAccount()/OnSystemRights()`, `DocumentUnderLegalHoldException`, `DocumentCheckedOutException`, `DocumentNameConflictException.OnTargetFolder()/OnSameParent()`).

**Prefer specific, intent-named exceptions over bare generic ones everywhere — not just `ApiException`.** The same rule extends to non-API exceptions thrown by domain/application logic: for a real error *condition*, throw a dedicated, intent-named subclass rather than a bare `throw new Exception("…")` / `InvalidOperationException("…")` / `ArgumentException("…")` with an ad-hoc string — name the type for the intent, and give a family a small shared base where a caller might `catch` the whole group. **Reserve the bare framework exceptions for genuinely generic, defensive, or unreachable cases**: argument guards (`ArgumentNullException.ThrowIfNull(x)`, `ArgumentException`/`ArgumentOutOfRangeException` for direct API misuse), and "this should never happen" assertions — these need no bespoke type. (One deliberate exception to the rule: `SimplArchiveDbContext.SaveChanges`/`SaveChangesAsync` throw `InvalidOperationException` for their invariants — cycle/sibling-name/required-field — which the Api boundary catches and translates into the specific `ApiException` subclasses; converting those DbContext throws to dedicated domain-exception types is a possible future cleanup, not required.)

## Documentation maintenance process

Every design-phase architectural decision now lives under `docs/adr/` (see the index at `docs/adr/README.md`) rather than in this file — CLAUDE.md itself is kept lean: what's needed to operate in the repo, plus pointers into the ADRs for rationale.

- New architectural/design decisions get their own new ADR (next sequential number under `docs/adr/`) rather than being written directly into CLAUDE.md.
- Whenever a PR implements a piece of already-planned architecture, that **same PR must update the corresponding documentation** (the relevant ADR and/or CLAUDE.md section) to reflect what was actually built, converting it from "planned" to describing the real thing — not left as a follow-up task, and not batched into periodic doc-only passes.

## API architecture (ADR 0003)

ADR 0003 commits the Api to HATEOAS, RFC 7807 Problem Details errors, media-type/Accept-header versioning, ETag/`If-Match` on every mutation, and independent JSON/XML content negotiation. **All five pieces now exist** — see `docs/adr/0187-hypermedia-envelope-and-problem-details.md`, `docs/adr/0188-etag-if-match-concurrency.md`, `docs/adr/0189-media-type-api-versioning.md`, `docs/adr/0190-json-xml-content-negotiation.md`.

**Standing convention — RESTful naming over RPC:** whenever you add or touch an endpoint, review whether it reads as a **resource** acted on with the standard HTTP methods rather than an **RPC verb-phrase** route. Prefer nouns and sub-resources over verbs in the path. Use `POST` on an action sub-resource only when a state transition genuinely isn't a plain create/replace/delete (e.g. `POST …/restore`, `POST …/rotate-secret`, `POST /search/reindex`); flag any new verb-in-path route and justify it against a resource-oriented alternative before committing.

- **All resource/diagnostics/root controllers are routed under an `/api` prefix** — each controller's `[Route(...)]` carries the literal `api/…` prefix (explicit per-controller, not a global convention, so the served path stays greppable), `RootController` is `[Route("api")]` (so `GET /api` is the discovery document and `GET /` falls through to the SPA). All hypermedia hrefs are correspondingly `/api/…`. **Protocol/infra endpoints deliberately stay at root**: `/connect/token`+`/connect/authorize` (OpenIddict, `~/connect/…` absolute routes), `/.well-known/openid-configuration`, `/health/live`+`/health/ready`, `/Account/Login`. A new controller must include the `api/` prefix in its route to stay consistent. The Blazor Client calls the `api/…` paths; OIDC is unaffected (its endpoints never moved).

- **OpenAPI definition** : alongside the HATEOAS hypermedia model, the Api serves a machine-readable **OpenAPI** document via the built-in **`Microsoft.AspNetCore.OpenApi`** (no third-party generator) — `builder.Services.AddOpenApi()` + `app.MapOpenApi().AllowAnonymous()` → **`GET /openapi/v1.json`**, served in **every** environment, anonymous (like `GET /api` + `/health/*`); **Scalar** (`Scalar.AspNetCore`, MIT) renders a browsable UI at **`/scalar`** mapped **only in Development**. `/openapi` + `/scalar` sit **outside `/api`**, so `VersionedContentTypeMiddleware` leaves the standard `application/json` content type alone (importers require it). The `GET /api` discovery document gained an **`openApi`** link. Minimal auto-generation (from controllers/DTOs — no XML doc comments yet). **`Microsoft.OpenApi` is pinned to `2.7.5`** in the Api project — `Microsoft.AspNetCore.OpenApi 10.0.9` floors it at the vulnerable `2.0.0` (advisory GHSA-v5pm-xwqc-g5wc / NU1903, vulnerable ≤ 2.7.4), so the pin keeps the CI vuln gate green (same transitive-security-pin pattern as `System.Security.Cryptography.Xml`). Verified: E2E `OpenApiEndpointTests` (anonymous spec with real routes + `application/json`, dev-only Scalar, the `openApi` discovery link). **Deferred**: XML-doc-comment descriptions, per-version documents reflecting the media-type versioning (ADR 0189), and an OAuth2/OIDC security scheme for Scalar's "try it".

- **Payload conventions already satisfied by ASP.NET Core defaults, nothing built for them**: camelCase (default `System.Text.Json` casing), explicit nulls (STJ's default — fields aren't omitted), ISO 8601 dates (`DateTimeOffset`'s default STJ serialization).
- **Problem Details**: `builder.Services.AddProblemDetails()` + `app.UseExceptionHandler()` in `Program.cs` lets application code throw with a specific, stable `errorCode`; any other unhandled exception falls back to a generic 500 with `errorCode = "INTERNAL_ERROR"`. **`IExceptionHandler.TryHandleAsync` must explicitly write the response with `contentType: "application/problem+json"`** — `HttpResponse.WriteAsJsonAsync` defaults to plain `application/json` otherwise, which doesn't match RFC 7807's own media type (ADR 0012). Discovered and fixed via the live-Api verification below.
- **ETag / If-Match**: every implementing entity automatically gets `ConcurrencyToken` configured as an EF Core concurrency token in `OnModelCreating` regenerate it to a fresh `Guid` for every `Added`/`Modified` entity (never set it manually. **A real `ConcurrencyToken` column, not a content hash** — portable across PostgreSQL/SQLite, unlike Postgres's built-in `xmin` system column, which would break SQLite test parity. The textbook EF Core concurrency pattern: a mutating handler sets the tracked entity's **original** `ConcurrencyToken` value (via `_dbContext.Entry(x).Property(e => e.ConcurrencyToken).OriginalValue = <If-Match value>`) before `SaveChangesAsync`, so a stale token makes EF Core's generated `UPDATE ... WHERE ConcurrencyToken = @original` affect zero rows and throw `DbUpdateConcurrencyException` — caught and translated to **412 Precondition Failed** with `errorCode: "ETAG_MISMATCH"` (ADR 0012's own example value); a missing `If-Match` header is **428 Precondition Required** with `errorCode: "IF_MATCH_REQUIRED"`.
- **Standing convention: every `GET` action has a companion `HEAD` action** — its own separate action (ASP.NET Core doesn't strip a `GET` action's body for `HEAD` automatically), returning the same headers with no body. Applied across every controller: `RootController`, `RepositoriesController` (all three `GET`s), `DocumentsController` (including `children`), `DocumentVersionsController`, `AclEntriesController` (both the list and the single-grant `GET`), `ServiceAccountsController` (both the list and single-account `GET`), `UsersController` (both the list and single-user `GET`), `GroupsController` (the list, single-group, and members `GET`s), `PlatformAdministratorsController` (both the list and single-admin `GET`), `TenantsController` (both the list and single-tenant `GET`), `DiagnosticsController.WhoAmI` — except `DiagnosticsController`'s two deliberate error-throwing test routes, which aren't "fetch a resource" endpoints.
- Verified end-to-end against a running Api instance: `/diagnostics/whoami`
- **JSON/XML content negotiation** : `AddXmlSerializerFormatters()` in `Program.cs` registers the standard XML input/output formatters. **Every response/request DTO across all three controllers was converted from a `record` (positional constructor / `init`-only properties) to a plain mutable class with a parameterless constructor** (`HypermediaResource`/`Link`, `WhoAmIResource` — `System.Xml.Serialization.XmlSerializer` needs that shape; `init`-only records aren't reliably deserializable by it. A nullable value type (`Guid?`) needs `[XmlElement(IsNullable = true)]` to serialize at all, regardless of whether it's ever actually null at runtime (`WhoAmIResource.TenantId`/`ServiceAccountId`). **Mechanism ended up simpler than a header-rewriting middleware** (which risked double-consuming the `Accept` header before `Asp.Versioning`'s own reader saw it): the vendor+version+format media types are added directly to each formatter's own `SupportedMediaTypes` list in `Program.cs`, so ASP.NET Core's built-in negotiation matches them with no rewriting needed. `VersionedContentTypeMiddleware` now detects whichever format was actually written (`application/json` vs `application/xml`/`text/xml`) rather than always assuming JSON. Verified live against a running Api instance: all four combinations (`Accept`/`Content-Type` in JSON↔XML, XML↔JSON, JSON↔JSON, XML↔XML) produce correct bodies and matching `Content-Type` headers, including a nullable-`Guid` resource (`whoami`) and a hypermedia resource with a nested `Links` collection.
- **`RootController`: the first true HATEOAS entrypoint chain. `GET /` (`RootController`, public, no auth), `admin` (not yet implemented — the link exists, the target doesn't).
- Verified end-to-end against a real Postgres + running Api instance: `GET /` reachable with no token and not swallowed by the SPA fallback route;

## Docker & Kubernetes
- `Dockerfile` at the repo root is a multi-stage build using the latest official Microsoft .NET Alpine images (`mcr.microsoft.com/dotnet/sdk:10.0-alpine` for build, `mcr.microsoft.com/dotnet/aspnet:10.0-alpine` for runtime), running as a non-root user and exposing port 9070.
- Its `HEALTHCHECK` targets `/health/ready` for plain `docker run`/docker-compose usage; Kubernetes deployments use their own separate liveness/readiness/startup probes against `/health/live` and `/health/ready` rather than relying on this Docker-level check. **Both endpoints are now implemented** — see `docs/adr/0205-health-check-endpoints.md` and the Api architecture section below; the container's reported health status is accurate.
- Verified end-to-end by building the image and running it: the base `mcr.microsoft.com/dotnet/aspnet:10.0-alpine` image already ships a non-root `app` user/group (UID/GID 1654) — the Dockerfile no longer runs `addgroup`/`adduser` for this, since that now fails with "group already in use" on current image builds.
- **`docker-compose.yaml`** at the repo root is a **local development / demo** stack — `docker compose up --build` runs the Api (built from the `Dockerfile`) plus `db` (`postgres:16-alpine`)
- **Crash resilience** : every long-running service carries **`restart: unless-stopped`** A single portable change → applies to both Docker and Podman. **Crash behaviour:** Docker's daemon restarts on crash; Podman's conmon restarts a genuinely-crashed (process-exited) container natively (a *user* `podman stop`/`kill` is correctly not restarted — that's `unless-stopped`). **Reboot:** Docker Desktop restarts them on daemon start; Podman does **not** after a machine reboot unless **`podman-restart.service`** is enabled (Podman 6 starts `always`+`unless-stopped` containers via its `should-start-on-boot=true` filter) — enable once per machine: `podman machine ssh 'systemctl --user enable podman-restart.service && sudo loginctl enable-linger $(id -un)'` (rootless/default machine).
- **Podman parity** : the **same `docker-compose.yaml`** runs unmodified under Podman via **`podman compose up --build`** — there is **no separate Podman config**, so there's nothing to keep in sync (one shared file). `podman compose` uses an external compose provider (the `docker-compose` Compose-v2 binary, which honors the `depends_on` conditions + `HEALTHCHECK`s the stack relies on) pointed at the Podman socket. macOS first needs a VM: `podman machine init --cpus 4 --memory 6144 --disk-size 40 && podman machine start`. **Standing rule:** since it's one file, any compose change applies to both engines automatically; if a future change ever breaks Podman, fix it with a portable value in the shared `docker-compose.yaml` rather than adding a Podman-only file.
