# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

**SimplCalCon** is a multi-tenant server (Clean Architecture, .NET) for storing and synchronizing **calendar entries (events and tasks)** and **contacts** across devices (smartphones, tablets, computers) via **CalDAV/CardDAV**, plus a **REST API** and a **Blazor WASM web UI** for editing, viewing, sharing, and backup.

The specification lives in `docs/spec.md`; the top-level `README.md` is the public overview (keep it in sync — see the README rule below); the task-oriented user/operator manual is `docs/manual.md` (native-client CalDAV/CardDAV setup, pgAdmin access — keep it current as operator-facing features land); every architectural decision is an ADR under `docs/adr/` (index: `docs/adr/README.md`). **Substantial code exists** — CalDAV/CardDAV, REST API, Blazor WASM client, multi-tenancy, ACL sharing, scheduling, data portability, and Docker/K8s packaging are built (ADRs 0001–0042+). Keep this file current as structure lands; do not let it go stale.

## Working with the user

Before writing any code or making any architectural/design decision, stop and interview the user first: ask questions, lay out the realistic options with their tradeoffs, and let them choose. Do not default to picking an approach and proceeding — decisions here are made collaboratively, one topic at a time.

Before making any automated database schema change (new/modified entities, EF Core configuration, migrations), show the user the proposed new schema and what it modifies — new tables/columns, changed constraints/indexes, affected existing tables — and get their go-ahead before generating the migration and applying it.

## Architecture Decision Records

All design-phase architectural decisions are recorded as ADRs under `docs/adr/` — see `docs/adr/README.md` for the index. Consult the relevant ADR before touching an area it covers; add a new ADR (next sequential number) rather than editing an old one when a decision changes.

- New architectural/design decisions get their own new ADR rather than being written directly into CLAUDE.md — this file stays lean: what's needed to operate in the repo, plus pointers into the ADRs for rationale.
- Whenever a PR implements a piece of already-planned architecture, that **same PR must update the corresponding documentation** (the relevant ADR, `docs/spec.md`, and/or a CLAUDE.md section) to reflect what was actually built — not left as a follow-up task.
- **Keep the top-level `README.md` current — it must never go out of sync.** Whenever a change affects what the project does, how it's run, or how it's deployed, update `README.md` in the **same PR**. The README is the public face and must always cover: what SimplCalCon is, the **Docker Compose** quick start, **production installation** (container image / Helm chart, DB provider, OIDC certificates), a link to the **user manual** (`docs/manual.md`), and the **showcase framing** — that this repository demonstrates how a senior, AI-driven software developer can produce a complex, production-shaped system in a relatively short period of time.

Seed decisions at a glance: .NET + EF Core with **PostgreSQL and SQLite both as configurable production databases** (ADR 0001 — everything must work on both providers); dual protocol surface `/dav` + `/api` (0002); DAV protocol layer implemented in-house (0003); hybrid blob-plus-indexed-fields storage (0004); OIDC + per-device app passwords (0005); multi-tenancy with platform/tenant admins (0006); full ACL sharing (0007); events + tasks with internal-first scheduling (0008); REST conventions = house suite minus XML (0009); Blazor WASM UI (0010); trash + version history (0011); sync-token/CTag + WebDAV-Push + SignalR (0012); import/export/takeout/migration (0013); medium scale target (0014); inherited conventions (0015).

## Code style

Prefer C# string interpolation (`$"{a}-{b}"`) over `+`-based string concatenation wherever practical, for readability.

Prefer switch expressions (`x switch { ... }`) over traditional `switch`/`case` statements wherever practical.

**Treat compiler warnings as errors.** A change is not done while it introduces (or leaves) a build warning — fix the underlying cause rather than suppressing it. Enforce via `Directory.Build.props` with `<TreatWarningsAsErrors>true</TreatWarningsAsErrors>` repo-wide (every project incl. tests). NuGet package-audit warnings (`NU1901`–`NU1904`) are excluded via `<WarningsNotAsErrors>` — a dedicated CI vulnerable-dependency scan owns vulnerability-blocking, so a freshly-published advisory can't break every compile mid-task. (Watch for the XML-comment `--` trap in that props file: a literal double-hyphen — e.g. writing out a `--flag` — makes the file fail to load with a misleading "Invalid framework identifier ''" restore error.)

**Use specific exception types, not bare `ApiException` with a string code.** Throw a dedicated, intent-named subclass that encapsulates code/status/message. Exceptions form a **two-level hierarchy**: a per-area **base** class inherits from `ApiException`, and each concrete error inherits from that area base, so a caller can `catch` a whole area or a single error. One file per class, `Exception` suffix, under an `Errors/Exceptions/<Area>/` folder in the Api project. The global handler translates any `ApiException` into the RFC 7807 response. Cross-cutting codes shared by several endpoints get one exception with static factories. Add a `NoBareApiExceptionTests`-style unit test early that scans `src/` and fails the build if a bare `new ApiException(...)` appears.

**Prefer specific, intent-named exceptions over bare generic ones everywhere — not just `ApiException`.** For a real error *condition* in domain/application logic, throw a dedicated, intent-named subclass rather than a bare `Exception`/`InvalidOperationException`/`ArgumentException` with an ad-hoc string; give a family a small shared base where a caller might `catch` the group. **Reserve bare framework exceptions for genuinely generic, defensive, or unreachable cases**: argument guards (`ArgumentNullException.ThrowIfNull(x)` etc.) and "this should never happen" assertions.

## Logging (ADR 0033)

Application logging is **Serilog** via `ILogger<T>` (structured message templates with
named properties — never string-concatenated messages; Serilog is wired only in
`Program.cs`, app code stays on `ILogger`). Levels are configured in the `Serilog`
section of `appsettings*.json` (framework/EF Core noise floored at Warning); the console
sink is human-readable in Development and compact JSON elsewhere.

**Grade every log by operator intent** — this six-level scale is a hard convention; a
mis-graded log is a defect (`ILogger` method in parentheses):

- **Trace** (`LogTrace`) — most verbose, *may clutter*: full payloads (blobs/bodies), per-item detail. Off in normal operation.
- **Debug** (`LogDebug`) — verbose, *no clutter*: normal control-flow milestones (write stored, message delivered, auth ok, skip taken).
- **Information** (`LogInformation`) — *clear, no clutter*: one line per meaningful outcome (request summary, a scheduling REQUEST/REPLY/CANCEL, bootstrap steps).
- **Warning** (`LogWarning`) — *high probability an admin must act*: degraded-but-serving (e.g. invited admin awaiting activation).
- **Error** (`LogError`) — *an exception for an admin to investigate*: unexpected faults (5xx), always with the exception object.
- **Fatal** (`LogCritical`) — *service impaired*: the process cannot serve (startup/host failure).

Per-request summaries come from `UseSerilogRequestLogging` (`/health/*` at Debug, 5xx/exceptions at Error); startup failures are logged **Fatal** in `Program.cs`'s host-run try/catch. Never log secrets (app-password/OIDC), even at Trace. Instrument the **key seams**, not every method.

**DAV wire trace:** `DavWireTraceMiddleware` logs the full `/dav` request/response bodies (CalDAV + CardDAV) at **Trace** for native-client diagnosis — off by default, gated on `IsEnabled(Trace)` for the `SimplCalCon.Dav.Wire` category (enable via `Serilog__MinimumLevel__Override__SimplCalCon.Dav.Wire=Verbose`), pass-through with no buffering when off. The first trace entry per process raises a one-time **Warning** (it captures contact/calendar payloads — leave it off in production). The same middleware also **Warns on unhandled DAV requests** (405/501, deduped, naming the client User-Agent) *regardless of trace level* — so native-client compatibility gaps surface in normal operation and point to enabling verbose for details.

## API architecture (ADR 0009)

The `/api` REST surface follows: HATEOAS hypermedia envelopes (`GET /api` is the discovery document), RFC 7807 problem details written with `contentType: "application/problem+json"`, ETag/`If-Match` on every mutation (412 `ETAG_MISMATCH`, 428 `IF_MATCH_REQUIRED`) backed by explicit `Guid` concurrency-token columns (regenerated on every save, portable across PostgreSQL/SQLite — never a DB system column), and **JSON only** (no XML formatters — the DAV surface is the XML protocol here; DTOs may be records). **Media-type versioning is deferred** (ADR 0019): v1 ships implicitly as `application/json`; add negotiation when a v2 exists.

**As built (ADR 0019):** `HypermediaResource`/`Link`/`CollectionResource<T>` envelope in `Api/Hypermedia`; the global `ProblemDetailsExceptionHandler` (`IExceptionHandler`) with the abstract `ApiException` base + per-area concrete subclasses in `Api/Errors/Exceptions/<Area>/` (guarded by `NoBareApiExceptionTests`); ETag/If-Match via a global `ETagResultFilter` (stamps ETag from `IETaggedResource`) + the `[RequireIfMatch]` action filter (the write path sets the EF `OriginalValue`, so a stale token → `DbUpdateConcurrencyException` → 412). Live resources so far: `GET /api` (public discovery), `GET /api/me`, and `GET/HEAD/POST/DELETE /api/app-passwords` (create returns the secret once). **Gotcha:** the `SimplCalCon.Api.Errors` namespace shadows OpenIddict's static-imported `Errors` constants — fully-qualify `OpenIddictConstants.Errors` at those sites.

- **RESTful naming over RPC**: prefer nouns/sub-resources; a `POST` action sub-resource only for genuine state transitions — flag and justify any new verb-in-path route.
- **All resource/diagnostics/root controllers route under a literal `api/` prefix** (explicit per controller, greppable). Protocol/infra endpoints stay at root: `/dav` + `/.well-known/caldav`+`/.well-known/carddav` (DAV, ADR 0002/0003), `/connect/*` + `/.well-known/openid-configuration` (OpenIddict), `/health/live` + `/health/ready`, `/openapi/v1.json` (all environments, anonymous) + `/scalar` (Development only). `GET /` falls through to the Blazor SPA.
- **Every `GET` action gets a companion `HEAD` action** (ASP.NET Core doesn't derive it automatically).

The **`/dav` surface is exempt from the REST conventions** — it follows the WebDAV/CalDAV/CardDAV RFCs (its own XML, ETag, and error semantics; see ADR 0003 for the supported-feature list).

## Sharing / ACL (ADR 0007, 0023)

**Built.** `AclEntry` grants `[Flags] AclRight` (Read/WriteContent/Create/Delete/Share/Admin) to a principal (user or group) on a collection; unique per (collection, principal); owner holds all implicitly. `IAclService` (Infrastructure `Storage/AclService`) evaluates effective rights = owner-all, else union of the user's direct grants and grants to any group they belong to **transitively** (`PrincipalGraph` BFS). **Cross-tenant grants rejected**; **tenant admins get no implicit access**. Enforcement (DAV): `read` → PROPFIND/REPORT/GET, `write-content` → object PUT/DELETE, collection-level ops (MKCOL/MKCALENDAR, DELETE collection) owner-only — via `DavControllerBase.HasAccessAsync` (owner-or-granted); the object store stays trusted. Shared collections appear in the sharee's home-set at the **owner's URL** (`ListAccessible{AddressBooks,Calendars}Async`). **Management (ADR 0026 + 0046):** REST grants via `SharesController` (`GET`/`PUT`/`DELETE …/{calendars|address-books}/{id}/shares/{principalId}`, `share`-right-gated) + DAV `current-user-privilege-set` reflects real grants (`DavPrivileges.From`). Web UI: a reusable **`ShareEditor`** (role presets Viewer=read / Editor=+write-content / Manager=+share, editable in place — `PUT` replaces the grant — add-by-search, remove) opened from a **Share ribbon Modal** on Calendar + Contacts (the `/share/{kind}/{id}` route stays, rendering `ShareEditor`). **Shared with me:** `GET/HEAD /api/shared-with-me` (`SharedWithMeController`) → non-owned accessible collections with owner name + effective rights. **Shared by me (ADR 0058):** `GET/HEAD /api/shared-by-me` (`SharedByMeController`) → the caller's owned collections that have grants, each with its resolved shares (principal + rights via `ListGrantsAsync` + `IPrincipalDirectory`). The `/shared` page (linked from Overview) shows both sections, "shared by me" with a Manage link to the `ShareEditor`. **Group management (ADR 0059):** groups are managed on the **Admin tab, tenant-admin only** (not the per-collection ShareEditor — membership is tenant-wide, so owner-editing would be privilege escalation): `IGroupService` (`GroupService`) + `AdminController` `GET/POST /api/admin/groups`, `DELETE …/{id}`, `GET/PUT/DELETE …/{id}/members[/{principalId}]` (duplicate/cycle → 409; cycle caught from the DbContext invariant). A Groups section on the Admin tab creates/deletes groups + manages members via the principal search; the ShareEditor still grants to groups. Deferred: per-object ACLs; membership view inside the ShareEditor.

## DAV surface (ADR 0003, 0021, 0022)

**CardDAV and CalDAV are both built.** CalDAV (ADR 0022) mirrors CardDAV under `/dav/calendars/{userId}/{cal}/{name}` (`/.well-known/caldav` → `/dav/`); the principal advertises both `addressbook-home-set` and `calendar-home-set`. It adds MKCALENDAR (+ extended MKCOL) honoring a requested `supported-calendar-component-set`, VEVENT+VTODO, and **`calendar-query` time-range via on-the-fly recurrence expansion** — `IDavRepository.QueryCalendarObjectsAsync` SQL-prefilters then expands recurring candidates with Ical.Net in `CalendarOccurrence.OverlapsRange` (Infrastructure; the Api doesn't reference Ical.Net). No materialized occurrence index yet. Gotcha: `Calendar` collides with `System.Globalization.Calendar` (alias it). Deferred: free-busy + iTIP scheduling (Phase 2). **Query filters (ADR 0043):** `calendar-query` + `addressbook-query` filters are now **evaluated** (not superset) — `Api/Dav/Xml/DavFilterParser` parses the XML into a provider-agnostic model (`Application.Abstractions` `CalendarQueryFilter`/`ContactQueryFilter`), and `DavFilterEvaluator` (Infrastructure) reads properties from the blob at the line level, so any named property is filterable. v1: comp-filter component + time-range + `prop-filter`/`text-match`/`is-not-defined` (calendar allof; addressbook allof/anyof, CardDAV match-types + negate). A deliberate ADR-0004 exception scoped to the on-demand query REPORTs (sync/PROPFIND stay indexed-only). **DAV depth (ADR 0054):** `param-filter` is now evaluated (`DavParamFilter` on `DavPropFilter`; the evaluator reads a property line's parameters, quote-aware); **partial `calendar-data`/`address-data`** honor the `<comp>`/`<prop>` subset **as a tree — nested `<comp>` to any depth, exact per-parent (ADR 0073)** (`Api/Dav/Xml/DavDataRequest` → `CalendarDataRequest.Root`/`DavCompSelection.Comps`, applied by Infrastructure `IDavDataFormatter`/`DavDataFormatter` at the line level via a selection-node stack in multiget+query **and `sync-collection`** (ADR 0070) — always keeps VCALENDAR/VTIMEZONE/VCARD + UID/RECURRENCE-ID/VERSION); and **`calendar-data` `expand`** flattens recurring events into one VEVENT per occurrence (`CalendarObjectParser.ExpandForData`, Ical.Net). **`limit-recurrence-set` (ADR 0068):** `CalendarObjectParser.LimitRecurrenceSet` keeps the master + only overrides overlapping the window (RRULE intact; `expand` wins if both present) — **rebuilds** the calendar rather than removing, since master+overrides share a UID and Ical.Net's `Remove` matches by UID (would drop the master).

### CardDAV (ADR 0021)

Principal-scoped layout (no tenant in the path): `/dav/principals/{userId}/`, home `/dav/addressbooks/{userId}/`, collections `.../{book}/`, objects `.../{book}/{name}`; `/.well-known/carddav` → 301 `/dav/`. Operations: PROPFIND (Depth 0/1), GET/PUT/DELETE with ETag + If-Match/If-None-Match, REPORT (addressbook-multiget/query/sync-collection), extended MKCOL, OPTIONS. A default `contacts` address book is auto-provisioned on first home access. Sync-token is opaque = the collection `ChangeSequence` (ADR 0020); foreign/malformed → RFC 6578 `valid-sync-token` 403. Owner-only access (403 otherwise; ACL is a later unit). All `/dav` routes use the DAV Basic app-password scheme.

**Code**: `Api/Dav/` — custom `HttpPropfind`/`HttpReport`/`HttpMkcol` method attributes (routing already tolerates trailing slashes, so **one template per action** — duplicate with/without-slash templates cause `AmbiguousMatchException`); the in-house XML framework in `Api/Dav/Xml` (`DavNames`, `DavResource`, `MultiStatus`, `PropRequest`); read/query + provisioning via `IDavRepository`; object writes reuse `IObjectStore` (so DAV PUT/DELETE get revisions, tombstones, and the change-sequence bump). `addressbook-query`/`calendar-query` filters + `param-filter` are evaluated and `address-data`/`calendar-data` honor a requested prop subset + `expand` (ADR 0043/0054). Manual native-client acceptance is tracked in `docs/dav-client-matrix.md` (per-client setup in `docs/manual.md`, full dev-machine testing workflow incl. the internal-CA cert in `docs/dav-device-testing.md`; DAVx5 delta sync verified); **`scripts/dav-smoke.sh <base-url> <email> <app-pw>`** is a curl harness that runs a client-like discovery + CRUD round-trip against a **deployed** instance (validates auth/TLS the in-memory integration tests don't) before/while testing real clients.

## Persistence (EF Core)

PostgreSQL **and** SQLite are both production providers, configurable per deployment (ADR 0001): every schema, index, migration, and query must work on both — migrations are maintained per provider, CI tests run against both. **Cross-provider gotcha:** SQLite cannot `ORDER BY` a `DateTimeOffset` (Postgres can) — order such results client-side, or store a sortable representation for large sets (ADR 0019). Blob + extracted-field hybrid storage per ADR 0004: one application-layer write path keeps them in sync; DAV listings/sync/queries must never parse blobs at request time and must structurally exclude trashed objects (ADR 0011) and enforce tenant scoping (ADR 0006).

**Structure as built (ADR 0016, 0017):** the single `SimplCalConDbContext` and its `IEntityTypeConfiguration<T>` classes live in `SimplCalCon.Infrastructure` (references only provider-agnostic `Microsoft.EntityFrameworkCore.Relational`). Because EF Core keeps one model snapshot per context per migrations assembly, each provider has its own thin project holding its migrations + an `IDesignTimeDbContextFactory`: `SimplCalCon.Infrastructure.Sqlite` and `SimplCalCon.Infrastructure.Postgres`. `dotnet-ef` is a local tool (`dotnet tool restore` first). **A model change is not done until both provider migrations are regenerated** — `dotnet ef migrations add <Name> -p src/SimplCalCon.Infrastructure.<Provider> -s src/SimplCalCon.Infrastructure.<Provider> -o Migrations` for each. Per CLAUDE.md, show the user the proposed schema before generating/applying any migration.

**DbContext conventions:** `IHasConcurrencyToken.ConcurrencyToken` is configured as the EF concurrency token and regenerated to a fresh `Guid` on every insert/update in `SaveChanges` (never set by hand). DbContext invariants (currently the nested-group cycle check) throw `InvalidOperationException` for the Api boundary to translate. Enums are stored as strings; case-insensitive uniqueness uses normalized shadow columns (`NormalizedEmail`/`NormalizedName`), never a provider collation. **Datetimes are UTC-only in the DB** (clients localize): new columns are UTC `DateTime` and a model-wide value converter forces `Kind=Utc` (also making them orderable on SQLite, unlike `DateTimeOffset`); the older `DateTimeOffset` columns already hold UTC instants and are left as-is.

**Object store (ADR 0004, 0020):** hybrid blob-plus-indexed storage. `Collection` (TPH: `Calendar`/`AddressBook`) owns `CollectionObject`s (TPH: `CalendarObject`/`ContactObject`); the `Blob` is the source of truth, extracted fields are for querying. Every write appends an immutable `ObjectRevision` (full history, ADR 0011). The single write path is `IObjectStore` (Infrastructure `Storage/ObjectStore`): parse → validate → store blob → extract → save → append revision → bump the collection `ChangeSequence` (the sync backbone), in one transaction serialized by the collection's concurrency token. Parsers: **Ical.Net** (iCalendar) + **FolkerKinzel.VCards** (vCard), both MIT; UIDs extracted at the line level. `IObjectImportExport` does ICS/VCF bulk import/export. **Auto-retention (ADR 0060):** `RetentionSweepService` (BackgroundService, **opt-in**) periodically hard-purges trashed objects (+ their revisions) past `SimplCalCon:Retention:TrashRetentionDays` (0 = keep forever/disabled; `SweepHours`/`BatchSize` tune it) via `IRetentionService.PurgeTrashedBeforeAsync` — no `ChangeSequence` bump (clients saw the tombstone), draining in batches. The same sweep also hard-purges **collections** soft-deleted past `SimplCalCon:Retention:DeletedCollectionRetentionDays` (0 = disabled, opt-in) via `PurgeDeletedCollectionsBeforeAsync` (ADR 0077 — object subtree explicit, child tables via cascade); and prunes **live-object revision history** older than `SimplCalCon:Retention:RevisionRetentionDays` while always keeping the newest + at least `MaxRevisionsPerObject` per object (ADR 0080 — `PruneRevisionsAsync`; `RevisionNumber <= counter - keepMin` plain-comparison delete, provider-safe). Runs if **any** of the three retentions is enabled; all opt-in (0 = off). **Occurrence-window index (ADR 0061):** recurring **VEVENT**s are materialized into an indexed **`EventOccurrences`** table (`ObjectId`/`CollectionId`/`StartUtc`/`EndUtc`, index `(CollectionId, StartUtc)`) over a rolling `[now-PastDays, now+FutureDays]` window, rebuilt on every write by `OccurrenceIndexer` inside the write transaction (non-recurring events stay on `DtStartUtc`/`DtEndUtc`, no rows). `CalendarObject` carries coverage flags `OccurrencesComplete`/`OccurrencesFromUtc`/`OccurrencesUntilUtc` (DB default `false` so un-materialized/pre-migration rows fall back). `DavRepository.QueryOverlappingAsync` (both `calendar-query` time-range paths) answers overlap via an indexed `EXISTS` where the window **covers** the query, else falls back to `CalendarOccurrence.OverlapsRange` — same **true-overlap** semantics (ADR 0067), so index==fallback==pure-expansion (test-asserted). `OccurrenceRollForwardService` (BackgroundService, on by default, `SimplCalCon:Occurrences`) re-materializes aged/never-materialized objects via `ExecuteUpdate` — **must not bump the ETag** (an internal refresh isn't an edit → would cause spurious `If-Match` 412s). **Gotcha:** materialize *before* the object `SaveChanges` (one ETag regeneration, atomic with the revision); a pathological rule is capped at `MaxRowsPerObject` with `Until`=last-materialized-start. Deferred: grid-expansion (`QueryCalendarOccurrencesAsync`) still uses Ical.Net (needs per-occurrence override summary/location).

**Attendees & free/busy (ADR 0030 — Phase 2 slice 1):** events carry `ORGANIZER`/`ATTENDEE` in the blob, extracted into the indexed `EventAttendees` table (`ObjectId`, `Address`/`NormalizedAddress`, `CommonName`, `Role`/`ParticipationStatus` string-enums, `IsOrganizer`) — rebuilt from the blob on every write in `ObjectStore` (so DAV PUT and REST both populate it); calendar-object reads `Include` it. REST: `EventResource`/`EventWriteRequest` gain `attendees`/`organizer` (composer writes the lines); `GET /api/free-busy?address&fromUtc&toUtc` resolves the address to a tenant user and returns merged busy windows. **Free/busy** (`IFreeBusyService`) = merged opaque busy across a user's owned calendars, recurrence-expanded (Ical.Net). **CalDAV native path (RFC 6638/4791):** principal advertises `calendar-user-address-set` + `schedule-inbox/outbox-URL`; the schedule-outbox answers a free-busy `POST` (`schedule-response` per recipient); `free-busy-query` REPORT returns a VFREEBUSY. UI: add attendees on event create, shown with PARTSTAT. **`TRANSP:TRANSPARENT` events are excluded** from free/busy (RFC 5545): `FreeBusyService` skips them — per-occurrence via Ical.Net `Occurrence.Source.Transparency` on the recurring path, and a line-level `TRANSP:TRANSPARENT` check on the non-recurring path (no schema column). Simplifications: `free-busy-query` reports the calendar owner's aggregate; free/busy is tenant-internal. **Deferred (next slice):** iTIP delivery (inbox `METHOD:REQUEST`, accept/decline → `REPLY`), DAV auto-scheduling on PUT, email iMIP.

**iTIP scheduling (ADR 0031 — Phase 2 slice 2):** RFC 6638 server-side automatic scheduling, tenant-internal, `/dav`-only. Schema: `ScheduleInbox` collection subtype (TPH, auto-provisioned per user at `/dav/calendars/{userId}/inbox/`) + `ScheduleMessages` table (delivered iTIP messages, sync via `ChangeSequence`/tombstone). `ISchedulingService` (Infrastructure) hooks `CalDavObjectController` PUT/DELETE (with the pre-write blob): organizer PUT → `METHOD:REQUEST` to each local attendee's inbox (dropped attendee → CANCEL); attendee PUT with changed PARTSTAT → `METHOD:REPLY` to the organizer's inbox **+ auto-apply** the PARTSTAT to the organizer's copy; organizer DELETE → CANCEL to all; **attendee DELETE → `REPLY;PARTSTAT=DECLINED` to the organizer (ADR 0048)** (auto-applied to the organizer's copy). `EventsController` create/update/**delete** also hook scheduling (ADR 0045/0048), so the web path invites/cancels/declines too. iTIP inspect/build via `ItipCalendar` (Ical.Net; Api stays Ical.Net-free); the inbox is a functional collection (PROPFIND/sync-collection/GET/DELETE) in `CalDavScheduleController` via `IScheduleInboxRepository`. **Gotcha fixed:** `ObjectStore.RebuildAttendeesAsync` must delete attendee rows in SQL and insert via the context — never also `Clear()` the tracked nav (re-deletes → phantom `EventAttendee` concurrency conflict on any attended-event update). Deferred: recurring/delegation.

**REST + web-UI invitations (ADR 0045):** the web/REST view of the schedule-inbox. `IInvitationService` (Infrastructure `InvitationService`): `ListAsync` (pending `METHOD:REQUEST`s, parsed via `ItipCalendar.Inspect` which now also surfaces summary/start/end) + `RespondAsync` (accept/tentative → drop the event into the user's default calendar with their PARTSTAT; all three → `ISchedulingService.SendReplyAsync` REPLY-to-organizer + auto-apply, then drain the message). REST: `GET/HEAD /api/invitations`, `POST /api/invitations/respond {resourceName,response}`. **Web-created events now invite** — `EventsController` create/update call `ProcessWriteAsync` (like the DAV path), so adding attendees over REST delivers REQUESTs (import stays quiet — scheduling is hooked into the interactive endpoints, never `IObjectStore`). UI: `/invitations` page (Accept/Tentative/Decline), linked from the Calendar ribbon, plus an **unread-invitation bell badge** in the shell top-right (`GET /api/invitations/count` — counts REQUESTs without parsing blobs; `MainLayout` refreshes it live via SignalR — ADR 0049 — and on every navigation as a fallback). No schema change.

**Email iMIP — per-tenant SMTP (ADR 0047):** external recipients (no local inbox) now get an iMIP email when their tenant has SMTP configured. `SchedulingService.DeliverAsync` unifies delivery: local → inbox (returns the id so a REPLY can auto-apply), external → `IEmailSender.SendItipAsync` (MailKit, MIT) with a `multipart/alternative` text + `text/calendar; method=…` payload (RFC 6047), else logged/dropped. Per-tenant config = a 1:1 shared-PK **`TenantEmailSettings`** table; the SMTP **password is Data-Protection-encrypted** at rest (`TenantEmailSettingsService`; DP keys must be persisted in prod like the OIDC certs — dev ephemeral keys → re-enter after restart). Tenant admin edits via `GET/PUT /api/admin/email-settings` (password write-only, `hasPassword` flag) → an **Email (SMTP)** form on the Admin tab, with a **`POST /api/admin/email-settings/test {to}`** "send test email" button (`IEmailSender.SendAsync` plain email via `GetConfigAsync` — ignores `Enabled` so you can verify before enabling; SMTP errors surfaced).

**Inbound iMIP (ADR 0056):** external organizers/attendees can now reach the scheduling system. Shared **`IInboundItipProcessor`** (`InboundItipProcessor`, Infrastructure): MimeKit parses the raw RFC822 → the `text/calendar` part; routes by METHOD keyed off the iTIP **content** (resolving addresses to local active users across tenants) — **REQUEST**→each local attendee's schedule-inbox, **CANCEL**→inbox + soft-delete the matching event by UID, **REPLY**→apply the sender's PARTSTAT to the local organizer's copy (reuses inbox repo + `IObjectStore` + `ItipCalendar.ReadMethod`). Two opt-in transports: **`POST /api/inbound-imip`** (raw message; shared-secret `X-Inbound-Key` = `SimplCalCon:InboundEmail:ApiKey`, constant-time; **404 when unset**) for an MTA pipe/inbound webhook, and **`ImapInboundPoller`** (BackgroundService, MailKit IMAP, off by default via `SimplCalCon:InboundEmail:PollerEnabled`, per-tenant errors isolated, marks `\Seen`). **Schema:** `TenantEmailSettings` extended with inbound IMAP columns (`InboundEnabled`/`ImapHost`/`ImapPort`/`ImapUseSsl`/`ImapUsername`/`ImapPasswordEncrypted` DP-encrypted/`ImapFolder`) — migrations both providers; tenant admin edits an **Inbound (IMAP)** section on the Email form. No new NuGet (MailKit already present). Deferred: DKIM/SPF checks, per-occurrence merge.

**Data portability (ADR 0029):** per-collection `POST …/{id}/import` (multipart `IFormFile` + `onConflict=skip|replace`) → `ImportResultResource`, and `GET/HEAD …/{id}/export` (text/calendar|text/vcard download) on the calendars/address-books controllers, over the pre-existing `IObjectImportExport`. **Subscription feed (ADR 0069):** a revocable, **anonymous** read-only feed — `GET/HEAD /api/calendars/{id}/feed/{token}.ics` + `.../address-books/{id}/feed/{token}.vcf` (`FeedController`, `[AllowAnonymous]`, constant-time token compare → 404 on mismatch, reuses `ExportAsync`, bypasses ACL by design). Token = `Collection.FeedToken` (nullable, unique, on the base so both kinds get it); owner `PUT`/`DELETE …/{id}/feed` enable-reset/disable via `IDavRepository.SetFeedTokenAsync`; `feedToken` on the resource is owner-only; the Edit modal shows the copyable `https`/`webcal` URL. For Outlook/Apple/Google/Thunderbird "internet calendar" subscriptions (see `docs/outlook-gap-analysis.md`). **Conditional GET (ADR 0071):** the feed sets `ETag` = the collection's `ConcurrencyToken` (changes on any content/rename/colour change) + `Cache-Control: must-revalidate`, and returns **304 before exporting** when `If-None-Match` matches, so a polling subscriber skips the export/transfer when unchanged. **Zip-archive import (ADR 0039):** the same import endpoint auto-detects a zip (name/content-type/`PK` magic via `Portability.IsZip`) and fans out to every matching entry (`.ics` for a calendar / `.vcf` for an address book, recursively; others ignored) via `IObjectImportExport.ImportArchiveAsync`, aggregating outcomes over the unchanged single-doc `ImportAsync` — so a **Google Calendar export `.zip`** imports directly (corrupt archive → 400; client `accept=".ics,.zip"`/`".vcf,.zip"`). **Separate collections (ADR 0040):** a `separateCollections=true` form flag on the same endpoint (a checkbox shown for a `.zip`) routes to `ImportArchiveToNewCollectionsAsync`, which **creates a new collection per entry** (calendar per `.ics` / address book per `.vcf`) named from the file's `X-WR-CALNAME` else filename — recreating a Google export's structure; result carries `CreatedCollections`. A `mergeByName` flag (default true, ADR 0041) merges files that resolve to the same name into one collection (so a Google export that shares an `X-WR-CALNAME` doesn't duplicate).

**Collection management + entry move (ADR 0041, 0042):** **rename** a calendar/address book via `PUT /api/{calendars|address-books}/{id}` `{name}` (owner-only, If-Match, `RenameCollectionAsync` — display name only, URL unchanged); **delete** via the pre-existing owner-only soft-delete `DELETE` (a ribbon button → confirm modal **gated by a type-the-collection-name confirmation** — exact trimmed/case-sensitive match, the destructive button stays disabled until it matches; collection deletes only, bulk entry delete keeps its plain confirm — ADR 0074); **restore a soft-deleted collection (ADR 0075)** — owner-only `GET/HEAD /api/{calendars|address-books}/deleted` + If-Match-exempt `POST …/{id}/restore` (flips `IsDeleted`/`DeletedAt`, `DeletedAt` surfaced on the resources/DTOs), shown as a collapsible **"Deleted (N)"** footer with a ↺ restore in the `CollectionsPane` on both tabs; **permanently purge a deleted collection (ADR 0077)** — owner-only If-Match-exempt `DELETE …/{calendars|address-books}/deleted/{id}` (`Purge{Calendar,AddressBook}Async` = `Remove`+cascade over the whole FK graph, no orphans/no migration), a 🗑 pane action gated by the same type-the-name confirm (ADR 0074, irreversible) **plus a mandatory backup download (ADR 0078)** — the purge button unlocks only after both typing the name and downloading a backup via owner-only `GET/HEAD …/{calendars|address-books}/deleted/{id}/export` (`IObjectImportExport.ExportAsync(id, includeDeletedCollection:true, …)` lifts the `!IsDeleted` gate); no schema change; **move** a single entry via `POST …/{events|contacts}/{id}/move` `{targetId}` (verb sub-resource: read source blob → `IObjectStore.PutAsync` to target → delete from source; If-Match on source, `write-content` on both, same-kind/tenant, UID clash → 409 `MOVE_CONFLICT`). UI: Rename/Delete ribbon buttons + modals and a "Move to…" picker in the event/contact detail; modal checkboxes use the shared global `.form-check` (label is the flex row, not a squeezed left column). **Bulk move/delete (ADR 0055):** `POST …/{events|contacts}/bulk-delete {ids}` + `bulk-move {ids,targetId}` (verb sub-resources, `write-content`, **If-Match-exempt** — operate on current versions; return `BulkResultResource {succeeded,failed,failures}`; partial failure is reported, event bulk-delete still fires iTIP CANCEL). UI: a checkbox column + select-all in the Calendar **list** + Contacts list with a selection toolbar (Move to… / Delete / Clear). Account **takeout** (`/api/takeout`, `TakeoutController` + `IAccountTakeout`/`AccountTakeout`, `System.IO.Compression`): `GET` a self-describing ZIP (`manifest.json` + `calendars/*.ics` + `addressbooks/*.vcf`) of owned collections; `POST` ingests one, **always creating new collections** (existing untouched), for manual server-to-server migration. Bad/manifest-less archive → 400 `INVALID_TAKEOUT`. `Api/Http/Portability` centralizes file read/conflict-parse/download. UI: import/export on agenda + contacts, a Takeout page (linked from Home); authenticated downloads use the `simplDownload` JS helper. Deferred: automated cross-instance pull, merge-into-existing ingest, streaming large takeouts.

**Contact-photo caching (ADR 0037):** contact cards carry their PHOTO inline (base64/`data:`) or as an external URL (Google exports the latter — fragile: referrer-blocked in-browser, and dies over time). `GET/HEAD /api/address-books/{id}/contacts/{cid}/photo` (`read`) serves the photo via `IContactPhotoService` (Infrastructure `ContactPhotoService`): inline → decode & serve; external URL → serve fresh cache (7-day revalidate) else **fetch server-side** (no referrer problem), byte-guard, cache in the new **`ContactPhotos`** table (shared-PK 1:1 to the contact, like `UserProfilePhoto`); on **source failure with a cache present → serve cache + embed the bytes back into the card** (inline base64 via `IObjectStore`, so it syncs to DAV and becomes self-contained), then drop the cache row. `PHOTO` parse/replace is `VCardPhotoRef` (line-level, RFC 6350 unfolding — Api stays parser-free). **SSRF guard** (`SsrfSafeConnect`, the "ContactPhotos" `HttpClient` `ConnectCallback`): validates the *resolved IP at connect time* (blocks loopback/private/link-local/CGNAT/ULA/multicast — also defeats DNS-rebinding + internal redirects), http/https only, 5 s / ≤3 redirects / 5 MB / `image/*`. SPA detail pane fetches the endpoint (→ `data:` URL), retiring the old `referrerpolicy` workaround. **Background refresh (ADR 0057):** `ContactPhotoRefreshService` (BackgroundService, **on by default** — `SimplCalCon:ContactPhotos:RefreshEnabled/RefreshHours/BatchSize`) periodically calls `IContactPhotoService.RefreshStaleAsync(batch)`, which re-runs the lazy `ResolveUrlAsync` over stale (>7-day) caches — refreshing live URLs and self-healing dead ones (embed cached bytes into the card) without waiting for a view; orphaned caches are pruned. No schema change. Deferred: proactive first-cache, DAV-side caching, conditional revalidation.

**Trash & version history (ADR 0028):** objects soft-delete to a `trash` sub-collection and keep full `ObjectRevision` history; both are surfaced via REST + UI (objects only — collections unchanged). `IObjectStore` gains `RestoreAsync`/`PurgeAsync`/`PurgeTrashAsync` (Put + Restore share `MaterializeAsync`/`CommitObjectAsync`); `RevisionOperation.Restored` added (migration-free — string column). Endpoints under `…/events` and `…/contacts`: `GET/DELETE …/trash`, `DELETE/POST …/trash/{id}[/restore]`, `GET …/{id}/revisions`, `POST …/{id}/revisions/{n}/restore`. **Restore/purge/revision-restore are If-Match-exempt** recovery actions (deliberate ADR 0009 deviation). Restore appends a `Restored` revision + bumps `ChangeSequence`; purge hard-deletes (no bump — clients already saw the tombstone). Missing revision → 404 `REVISION_NOT_FOUND`. UI: per-collection Trash page + per-item History page.

## Authentication (ADR 0005, 0016, 0018)

Two auth surfaces over one identity store. **Web/REST** uses OpenIddict (auth code + PKCE + refresh + logout); the Blazor WASM app is a seeded public client (`simplcalcon-spa`). Interactive login is a cookie session from a minimal `/Account/Login`; every token exchange re-checks the account is Active. **Session renewal (ADR 0076):** the SPA requests `offline_access`, so it renews via the **refresh-token grant** (14-day sliding, rolling) — no dependency on the interactive cookie/iframe, surviving idle + browser restarts (access token 15 min). `offline_access` needed no server change (built-in scope, gated by the client's already-present RefreshToken grant). A centralized client `SessionExpiredHandler` (`DelegatingHandler` wrapping the auth handler) **redirects to login (return-URL preserved) on `AccessTokenNotAvailableException` or a `401`** so an ended session no longer strands the tab on broken 401s. **Auth hygiene (ADR 0079):** a `TokenPruneService` (BackgroundService, mirrors `RetentionSweepService`) periodically calls OpenIddict `IOpenIddictTokenManager.PruneAsync` then `IOpenIddictAuthorizationManager.PruneAsync` (that order) to clear invalid/expired tokens (rolling-refresh leaves redeemed rows) — **on by default**, `SimplCalCon:Auth:TokenPruneDays` (default 14, 0=disabled) + `PruneHours` (24); non-destructive (only already-invalid rows), no dep, no schema change. On expiry the handler sets an in-memory `SessionState.SessionExpired` flag that `Authentication.razor` reads once to show a brief **"session expired"** banner over `RemoteAuthenticatorView`. Dev uses ephemeral in-memory keys and disables the HTTPS-transport requirement; **production requires signing + encryption certificates from config and fails fast without them**. **DAV** uses HTTP Basic on `/dav` via `DavBasicAuthenticationHandler`, backed by per-device app passwords only (never the account password) — slow PBKDF2 hash at rest + a short-lived fast-verify cache keyed by a hash of (email, secret).

Account/app-password hashing is `PasswordHasher<T>` (PBKDF2) with rehash-on-login; policy is length-first (min 12) + denylist + lockout via the `AccessFailedCount`/`LockoutEnd` fields. Activation/reset tokens are SHA-256-hashed, single-use, expiring. The auth services live in `Infrastructure` behind `Application/Abstractions` ports; internal services are `internal` with `InternalsVisibleTo(SimplCalCon.UnitTests)`.

**Provider selection + first-run** happen in the Api host: it reads `SimplCalCon:Database:Provider` (`Sqlite`|`Postgres`) and passes the provider to `AddSimplCalConInfrastructure` (Infrastructure stays provider-agnostic). A bootstrap `IHostedService` migrates, seeds the SPA client + platform admin (password from config → Active, else Invited + activation link logged), and — Development only — an optional demo tenant/admin. Gotcha: OpenIddict's `HttpContext` helpers (`GetOpenIddictServerRequest`) are in the **`Microsoft.AspNetCore`** namespace. The integration test assembly disables test parallelization (WebApplicationFactory cold-start contention).

## Client (Blazor WASM)

**Built (ADR 0025).** Blazor WebAssembly app, **served by the Api host** (Api references the Client + `WebAssembly.Server`; `UseBlazorFrameworkFiles` + `MapFallbackToFile("index.html")` → `GET /` SPA, `/api` REST, `/dav` DAV — one deployable; the Dockerfile publishes the WASM). **WASM asset fingerprinting is disabled** (`WasmFingerprintAssets` + `BlazorFingerprintBlazorJs` = false in the Client csproj, and `index.html` references `_framework/blazor.webassembly.js` plainly): because the host serves the physical `index.html` via `MapFallbackToFile`, the .NET 9+ default `#[.{fingerprint}]` placeholder is **never resolved** in a published container (dev-time static-web-assets hide this — only the published image 404s the bootstrapper). Guarded by `SpaHostingTests.Spa_bootstrapper_reference_resolves_to_a_served_file`. Don't re-enable fingerprinting without switching the host to `MapStaticAssets`. OIDC (code + PKCE) via `WebAssembly.Authentication` against the seeded `simplcalcon-spa` client, with a `BaseAddressAuthorizationMessageHandler` attaching tokens to `/api` via a typed `ApiClient`. **Shell (ADR 0034):** `MainLayout` is a flex **column** — fixed top **ribbon** (contextual per-page buttons via a `SectionOutlet`/`SectionContent` named `RibbonSection`), a scrollable middle content region, and a **bottom tab bar** (Overview · Calendar · Contacts · Configuration · Admin, Admin shown only when `me.IsAdmin`). Top-right **account box** = `me.DisplayName` + round avatar (photo or **initials** fallback) with a self-service menu (Sign out; **Profile** → `/profile`). **Profile photo (ADR 0035):** a 1:1 shared-PK `UserProfilePhoto` table (client sends a normalized 256×256 PNG; server only byte-guards via `ProfilePhotoValidator` — no image library); `UsersController` (`api/users/{id}/photo` PUT/GET/HEAD/DELETE, self or tenant-admin-in-tenant); `GET /api/me` carries `HasPhoto`; the client crops in-browser (`photoCrop.js`, interactive pan/zoom) and renders the bearer-protected photo via an authenticated fetch → `data:` URL (a plain `<img src>` would 401). A reusable `AvatarEditor` component (parameterized by the photo `Path`) does view+change+remove, used for **self** on `/profile` and, for a **tenant admin**, for a selected user in the **Admin** tab. A separate lightweight read-only **`Avatar`** component (photo-or-initials, lazy-fetches only when `HasPhoto`) renders **per-row thumbnails in the Admin user list** — `AdminUserResource`/`AdminUserDto` carry a computed `HasPhoto` (exists-check on `UserProfilePhotos`, no schema change). No left menu. Identity + role come from `GET /api/me` (`MeDto`). Calendar/Contacts routes take an **optional** id (`/calendars/{id?}`, `/address-books/{id?}`) so the tab has a landing (auto-select first + ribbon switcher). **Configuration** (`/configuration`) = app-passwords + per-client CalDAV/CardDAV setup data (replaces `/app-passwords`). **Admin** (`/admin`) is role-gated via `AdminController` (`api/admin/tenants` platform-admin, `api/admin/users` tenant-admin; in-code role checks). Plain Razor + CSS (no component library). **The SPA's OIDC redirect origin must match the serving origin** — set `SimplCalCon:SpaClient:BaseUrl` to it (the seeded client's redirect URI; demo compose uses `http://localhost:9080`).

The REST resources the UI consumes (ADR 0009, 0025): `/api/calendars` + `/api/address-books` (list accessible/get/create/delete) with nested `.../{id}/events` (agenda via `?fromUtc&toUtc`) + `.../{id}/contacts` (list/get/create/update/delete). ACL-enforced (`read`/`write-content`) via `ApiControllerBase`; structured JSON in/out with `IObjectComposer` building the iCal/vCard blob (UID preserved on update). Deferred: rich editors. **UI test guards (ADR 0063):** `tests/SimplCalCon.WebTests` (**bUnit**, in `SimplCalCon.slnx` so CI runs it) renders components against a fake `/api` via the shared `ApiHarness` (canned-JSON `HttpMessageHandler` + stub token provider + inert `LiveUpdates` + loose JS interop + authorized user); guards cover `CollectionColors`, `CollectionsPane`, and the merged colour-coded `CalendarView`/`Contacts` views. Add page tests by registering canned GETs on `ApiHarness.UseFakeApi`. (Test-only `AngleSharp` `NU1902` is covered by the `NU19xx` `WarningsNotAsErrors`.)

**Live updates (ADR 0049):** the web client refreshes calendars/contacts + the invitation badge **live** over SignalR. `NotificationHub` at **`/hub/notifications`** (OpenIddict bearer; WebSockets pass the token in the `access_token` query, lifted into the `Authorization` header by a `/hub` middleware before `UseAuthentication`). Groups: per-user (`user:{id}`, auto-joined, invitation pushes) + per-collection (`collection:{id}`, joined via the `Subscribe(id)` hub method after a `read`-right check). Server signal = the **`IChangeNotifier`** port (Application): `ObjectStore` fires `CollectionChangedAsync` **post-commit** on Put/Restore/Delete (purge doesn't — no `ChangeSequence` bump), `ScheduleInboxRepository` fires `InvitationsChangedAsync(owner)` on deliver/drain; both wrapped so a push failure never fails the write. The **Api** implements it (`SignalRChangeNotifier`/`IHubContext`); **Infrastructure stays SignalR-free** (default `NoOpChangeNotifier`, registered in Infrastructure DI, overridden in the Api). Client `LiveUpdates` service (`Microsoft.AspNetCore.SignalR.Client`, MIT) manages the `HubConnection` (auto-reconnect, token via `IAccessTokenProvider`) and **debounces** `CollectionChanged` ~300 ms so a bulk import reloads once; `CalendarView`/`Contacts` subscribe to the shown collection + reload on change, `MainLayout` refreshes the badge on `InvitationsChanged`; refresh-on-navigation stays as the fallback. **Sharing live-refresh (ADR 0064):** `IChangeNotifier.SharesChangedAsync(userIds)` (SignalR `SharesChanged` to each `user:{id}`; no-op in NoOp/WebPush) fires **post-commit** from `AclService` grant/revoke (owner + grantee — a group grant fans out to transitive members via `PrincipalGraph.GetMemberUserIdsAsync`, the reverse of the ACL graph) and `GroupService` add/remove-member (the affected member's users); the `/shared` page (`SharedWithMe`) reloads both sections on the `LiveUpdates.SharesChanged` event. **Admin-list live refresh (ADR 0065):** `IChangeNotifier.AdminChangedAsync(tenantId)` (SignalR `AdminChanged` to `admin:tenant:{tenantId}`, which tenant admins auto-join in `NotificationHub.OnConnectedAsync` via the `role`+`tenant_id` claims) fires post-commit from `GroupService` create/delete/add-member/remove-member; `Admin.razor` reloads its group list on the `LiveUpdates.AdminChanged` event. Only the **group** list is live (tenants/users are read-only in-app). Deferred: presence.

**WebDAV-Push (ADR 0052):** native DAV clients (DAVx5) get pushed changes instead of polling, via the bitfire **WebDAV-Push** draft (`https://bitfire.at/webdav-push`) over Web Push (RFC 8030/8291/8292). Same signal as live updates: a **`WebPushChangeNotifier : IChangeNotifier`** fires on the post-commit `CollectionChangedAsync`, **composed with** the SignalR one by `CompositeChangeNotifier` (each transport isolated). Collections advertise `push:transports`/`push:topic`/`push:supported-triggers` in PROPFIND (`DavPushAdvertisement`) when enabled; clients `POST` a `push-register` to the collection (→ `204` + `Location` + `Expires`, stored in the `PushSubscriptions` table, FK→Collection, unique `(CollectionId,Endpoint)`) and `DELETE /dav/push-subscriptions/{id}` to unsubscribe (`WebDavPushController`). On change, the notifier encrypts a `push-message` (topic + `{DAV:}sync-token` matching `DavTokens.Format`) to each endpoint via the **WebPush** library (MIT), pruning `404/410`/expired. VAPID keys from `SimplCalCon:WebPush` (`VapidPublicKey`/`VapidPrivateKey`/`Subject`); **disabled when absent** (not fail-fast), **ephemeral in Development** (`AllowEphemeralKeys`, warns — resets on restart). Topic = base64url(collectionId) (`PushTopic.For`, shared Application). Real DAVx5 interop is **manual acceptance** (`docs/dav-client-matrix.md`); tests cover advertisement/register/fan-out/unregister with a capturing sender. **DAVx5 delivers push over UnifiedPush**, so the Android device needs a distributor app (**ntfy**) — without one it silently polls and never registers. **Server side verified end-to-end on-device:** advertisement + `push-register` (ntfy endpoints in `PushSubscriptions`) **and** encrypted `push-message` delivery — the RFC 8291 ciphertext was observed cached at the ntfy topic (`GET https://ntfy.sh/<topic>/json?poll=1`), one per change, no send error. The remaining unproven link is the device *waking*, which is device push-app/battery config (Android doze killing ntfy's socket), not a server concern. **Testing gotcha:** ephemeral VAPID keys rotate on every api restart → existing subscriptions invalidate → re-sync DAVx5 to re-register (persistent keys avoid it). Client/operator setup (VAPID keys, ntfy, battery-optimization troubleshooting) is in `docs/manual.md` → "Instant sync with WebDAV-Push". Deferred: property-update triggers, inbox push, key-rotation messages.

**Calendar list + grid views (ADR 0038):** the Calendar tab has a **List** view (default) and a **Calendar** grid view, toggled from the ribbon. List = a sortable/filterable/**resizable** event table (Start · Title · Location · Repeats) — per-column text filters + a Repeats "only" checkbox, `columnResize.js` reused from Contacts (the table stays in the DOM, hidden via CSS in grid mode, so widths persist). **Gotcha:** the resize grip `.col-grip` is injected into the DOM by JS, so it carries no Blazor CSS-isolation scope attribute and **must be styled in global `app.css`, not component-scoped `.razor.css`** (a scoped `.col-grip` rule silently never matches → ungrabbable columns). Grid = a **month/week** switcher, prev/next/today navigation, event chips → a detail `Modal` (When/Repeats/Location/Attendees + Edit/History/Split). The event editor + Import are ribbon `Modal`s. The **list** view fetches masters (one row per series, `↻` flags recurring); the **grid** fetches expanded occurrences for its visible window (ADR 0050). **Multi-day events (ADR 0072):** the grid shows an event's chip on **every day it covers** (`CalendarGrid.CoversDay` — end exclusive at midnight, so an all-day DTEND/00:00 end adds no day; start day shows the time, continuation days a `…`/`.chip-cont`); the grid expansion looks back so an event starting before the visible window still spans in. To show/search location, calendar objects extract an indexed **`Location`** column (`CalendarObject.Location`, from iCal `LOCATION` on every write, surfaced on `EventResource`/`EventDto`) — a schema addition, migrations both providers. Deferred: hourly day-grid, drag-to-move.

**Collections pane, colours & merged views (ADR 0062):** both the Calendar and Contacts tabs have a **left pane** (`CollectionsPane`, reusable) listing collections — each row a **visibility checkbox** (filter) + **colour swatch/picker** (native `<input type=color>`, owner-only) + **name** (click = *active*). The tabs render the **union** of all checked collections, each entry tagged with its collection's colour (`CollectionColors.For` = stored colour else a stable palette colour from the id); grid chips are tinted, and the list views gain a **colour column (1st)** + **collection column (2nd)**. This replaced the old ribbon collection dropdown. The **active** collection is the target for New/Import/Export/Rename/Delete/Share/Trash; per-entry actions (edit/delete/move/split/history, raw vCard, photo) target the entry's **own** collection (so an entry from a non-active collection still edits correctly); bulk move/delete groups the selection by source collection. Checked-set + active-id persist in **`localStorage`** per tab (`simplcal.{calendar,contacts}.{checked,active}`, default all-checked); the `/calendars/{id?}` + `/address-books/{id?}` routes still deep-link. Live updates subscribe to **all** checked collections. **Colour storage:** `Collection.Color` (nullable hex) — the column moved from `Calendar` to the base `Collection` (a model-only move, **empty migration**) so address books get it; set via the owner-only `PUT /api/{calendars|address-books}/{id}` extended to `{name, color}` (`CollectionUpdateRequest`, was `RenameCollectionAsync` → `UpdateCollectionAsync`), colour on `CalendarResource`/`AddressBookResource`/DTOs. Owner-set/shared; no CalDAV `calendar-color` sync. **Per-user colour (ADR 0066):** a `UserCollectionColors` table (`UserId`+`CollectionId` unique, `Color`) holds each user's **personal override**, layered over the owner colour — effective = `myColor ?? ownerColor ?? palette` (`CollectionColors.Effective`). Set/cleared via `PUT`/`DELETE /api/{calendars|address-books}/{id}/color` (`IUserCollectionColorService`, **read**-gated so sharees can recolour, no If-Match); `myColor` is surfaced on the resources/DTOs. The pane picker now sets the **personal** colour for everyone (+ a reset ↺); the owner sets the shared default in the **Edit** modal (owner PUT `{name,color}`). The pane (with its collapsible **"Deleted (N)"** restore/purge footer — ADR 0075/0077/0078) renders whenever there are live **or** deleted collections; the "none yet" message shows only when both are empty, so deleting your only collection never strands it.

**Recurring-event editing (ADR 0050):** a shared create/**edit** event editor (Summary, All-day, Start, **End**, **Location**, Attendees, **Repeat**) — the web UI previously had no edit form and couldn't set end/location/recurrence. Repeat = Daily/Weekly/Monthly/Yearly + interval + weekly **BYDAY** + end (never/until/after N), a structured `Recurrence` record with a hand-written `RecurrenceRule.TryParse`/`Format` (Application, no Ical.Net) shared by the Api + `ObjectComposer` (which now also emits `LOCATION`/`RRULE`). Rules beyond the subset (BYSETPOS, BYMONTHDAY, ordinal BYDAY…) → `recurrenceSupported=false`, shown **read-only** and **preserved verbatim** (the client echoes the raw `recurrenceRule` on save). **Schema:** indexed **`RecurrenceRule`** column (`varchar(1024)`, nullable) on `CollectionObject`, extracted from the `RRULE` line on every write (mirrors `Location`) so reads don't parse blobs — migrations both providers. **Grid expansion:** `GET …/events?fromUtc&toUtc&expand=true` → one item per occurrence (`IDavRepository.QueryCalendarOccurrencesAsync` + `CalendarOccurrence.Occurrences` via Ical.Net `GetOccurrences`), each carrying the master id, its **RECURRENCE-ID**, and its **effective summary/location** (an overridden instance shows its own — ADR 0051). Editor update uses `If-Match:*`.

**Per-instance edits + monthly Nth-weekday (ADR 0051, extends 0050):** monthly rules widen to **"on day N"** (`BYMONTHDAY`) or **a single ordinal weekday** (`BYDAY=2TU`/`-1FR`, ordinals 1–4/-1) — `Recurrence.ByMonthDay` + wider `RecurrenceRule` parse/format; richer rules still round-trip as read-only custom. **Per-instance:** editing/deleting a recurring **occurrence** (a grid item — carries `RecurrenceId`; list rows act on the whole series) prompts **This event / This and following / All**. `IRecurrenceEditor` (Infrastructure) applies RFC 5545 transforms via Ical.Net (`CalendarObjectParser.ExcludeOccurrence`=EXDATE / `SetOccurrenceOverride`=RECURRENCE-ID VEVENT / `TruncateSeriesBefore`=UNTIL) through `IObjectStore`; "this-and-following" edit truncates the master + composes a **new series** from the editor. Routes: `PUT`/`DELETE …/events/{id}/occurrences/{recurrenceId}?scope=this|following` (recurrence-id = the slot in basic form `yyyyMMddTHHmmssZ`; bad → 400 `INVALID_RECURRENCE_ID`). No schema change. **Ical.Net v5.2.3 gotchas:** `CalendarEvent.RecurrenceRule` (singular) / `RecurrenceIdentifier` (type `RecurrenceIdentifier`, read via `.StartTime.AsUtc`, construct `new RecurrenceIdentifier(new CalDateTime(...))`); `RecurrencePattern.Count`/`Until` are nullable; `ExceptionDates.Add(CalDateTime)`; `Occurrence.Source` gives the occurrence's component; **an occurrence's `Period.EndTime` is null — use `Period.EffectiveEndTime` (= start+duration) for its end** (ADR 0067; `EndTime ?? start` silently made recurring occurrences zero-duration). **Time-range = true RFC 4791 overlap (ADR 0067):** `OverlapsRange`/`Materialize`/free-busy expand from `windowStart − maxEventDuration` (look-back) and match `s < end && e >= start`, so an occurrence starting before a client's window but running into it is returned. **iTIP on per-instance edits (ADR 0053):** `EventsController.UpdateOccurrence`/`DeleteOccurrence` call `ISchedulingService.ProcessWriteAsync` with the pre/post whole-object blobs (like whole-series `Update`), so an organizer's override/EXDATE/truncate delivers a `METHOD:REQUEST` to attendees (inbox + iMIP); exclude/truncate is a modification (REQUEST reflecting the EXDATE/shortened rule), not a CANCEL, and a split invites both the shortened old series and the new one. Deferred: precise bare-RECURRENCE-ID CANCEL/REQUEST (uses whole-object REQUEST); attendee per-instance decline; `COUNT` not carried into a split tail.

**Contacts master-detail + raw vCard (ADR 0036):** the Contacts tab is a master-detail view — a sortable/selectable columns list (Name·Org·Email·Phone) on the left; a split detail on the right with the card's **photo** (client-parsed from the vCard by `VCardPhoto`) on top and the **raw vCard** below (read-only → Edit → Save/Cancel). New-address-book + Import moved to **ribbon buttons → `Modal`** (reusable). Backed by **raw vCard endpoints** `GET/PUT /api/address-books/{id}/contacts/{cid}/raw` (`text/vcard`, ETag + If-Match) — a deliberate, narrow exception to "structured JSON only" (ADR 0009), storing the edited text through the normal `IObjectStore` validate-and-extract path. The vCard is the source of truth (ADR 0004), so raw edits are lossless. **Validate-on-save:** the store parses and **persists only if valid**, else rolls back and returns `400 INVALID_VCARD` (or `409 VCARD_UID_CONFLICT`); the client keeps the editor open with the edits + shows the reason. The list has **per-column text filters + a tri-state Photo filter** (Any / With photo / Without photo, a `<select>` — ADR 0035/0036 polish); `ContactResource.HasPhoto` is a computed PHOTO-regex flag over the loaded blob (no schema change).

**Event splitting (ADR 0027):** `POST /api/calendars/{id}/events/{eventId}/split` `{ atUtc }` cuts one event into two same-kind events in the same calendar — original truncated to `atUtc` (UID kept), a fresh-UID copy covers the tail. `write-content` + If-Match; preconditions map to `CANNOT_SPLIT_RECURRING`/`EVENT_NOT_SPLITTABLE`/`SPLIT_POINT_OUT_OF_RANGE` (Api area `Errors/Exceptions/Calendars/`). The blob-preserving transform is `IEventSplitter` (Infrastructure `EventSplitter` + `CalendarObjectParser.SplitEventAt`, Ical.Net) — **not** `IObjectComposer`, so description/location survive; the agenda view offers a per-event Split control. Non-atomic across the two writes (copy created first). Deferred: recurring/VTODO/N-way splits.
